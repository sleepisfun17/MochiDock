## 3. Operational Gotchas

- **Do not launch `MochiDock.exe` through automated tools or subagents.** `MochiDock/app.manifest` requires Administrator privileges for ETW capture. `App.xaml.cs` enforces `Global\MochiDockSingleInstanceMutex`; another launch can show a blocking dialog. Leave application execution to the human user.
- Publishing into `Publish/` can fail while files are locked. `scripts\build_and_publish.bat` delegates to `scripts\publish.ps1`, which elevates, requests normal exit from exact destination instances, waits 10 seconds, then force-stops remaining matching instances. It publishes and validates project-managed assets before updating the Desktop shortcut. It never launches the app.
- The project copies the root GOWA binary, accompanying README and startup helpers into build/publish output. Never package session storage.
- Startup uses `MochiDock-Startup-<current-user-SID>`, an elevated interactive logon task with a 10-second delay. The tray and the install/uninstall scripts (`MochiDock/Scripts/`, copied next to the exe) manage the same task; ordinary settings saves do not register startup. Use the scripts from an elevated shell for the same administrator account. Legacy Run/Startup registrations migrate only when unverified (`!enabled && legacy`), preventing repeated `powershell.exe install-startup.ps1` execution on cold application launches. `MainWindow_Loaded` executes layout positioning, sizing, and theming synchronously before backgrounding startup verification, eliminating cold launch UI freezes.

## 4. Architecture and Storage

- **Stack:** C# 12 with the .NET 8 SDK defaults, targeting `net8.0-windows10.0.19041.0`; WPF with Windows Forms support, nullable references and implicit usings enabled. The project does not explicitly pin a C# language version. Direct packages are SQLite, TraceEvent and System.Management; see `MochiDock/MochiDock.csproj` for versions.
- **Composition:** `MochiDock/App.xaml.cs` constructs services and injects them into `MochiDock/ViewModels/MainViewModel.cs`. The view model also creates hardware and audio services. Services publish C# events; the view model implements `INotifyPropertyChanged` and exposes bound collections. Card code-behind commonly calls view-model methods directly.
- **Window:** `MochiDock/MainWindow.xaml(.cs)` owns overlay layout, animation, hover behavior, tray integration and positioning. `MochiDock/Services/MultiMonitorHelper.cs` handles monitor selection and DPI coordinate helpers. `WS_EX_TOOLWINDOW` is applied in `MainWindow_Loaded` for Alt+Tab exclusion.
- **Other modules:** `MochiDock/Models/` holds settings and feature data; `MochiDock/Services/` implements integrations and persistence; `MochiDock/Controls/` contains the mascot, marquee and progress controls.

| State | Location and ownership |
| :--- | :--- |
| Settings | `%AppData%\MochiDock\settings.json`; `SettingsService.cs` migrates legacy `settings.json` from the executable directory |
| Tasks | `%AppData%\MochiDock\tasks.json`; `TasksService.cs` |
| GOWA session | `%LocalAppData%\MochiDock\GOWA\storages`; persistent daemon working data, separate from published binaries |
| Phone uploads | `%LocalAppData%\MochiDock\PairedDrop`; `FileShelfService.cs` |
| Clipboard history and shelf membership | In-memory collections; uploaded files remain on disk |
| FX rates | Atomic cache and rolling request ledger at `%LocalAppData%\MochiDock\FxRates\rates.json`; version 2 keyless pair quotes and history; old Windows credentials remain untouched and unused |
| Lyrics cache | Bounded memory and disk cache in `LrclibService.cs`; `%LocalAppData%/MochiDock/Lyrics` |

Mailspring's SQLite database is an external, read-only integration; MochiDock has no application database migration system. Preserve the `MochiDock` storage, registry and mutex identities, existing settings defaults and migration compatibility when changing persistence.

## 5. Integrations and Current Limitations

- **GOWA:** `MochiDock/Services/GowaService.cs` supports local and remote modes. Local lookup uses `<executable directory>/GOWA/windows-amd64.exe`; missing binaries are logged without a developer-path fallback. `%LocalAppData%\MochiDock\GOWA` is the working/session directory, not an executable lookup path.
- **PawnIO is optional and never bundled** (proprietary freeware kernel driver). `SensorService.IsPawnIoInstalled` drives the Hardware settings "CPU sensors" row (Get PawnIO, Copy winget command); the app never installs or runs it. The installer's unchecked `pawnio` task runs `winget install --id namazso.PawnIO --exact --source winget --silent --accept-package-agreements --accept-source-agreements` in `[Code]` (`InstallPawnIo`, exit codes 0 and 3010 count as success) and only shows a message when winget is missing or fails; the setup never fails because of it.
- **Power chip and history:** `MainViewModel.SamplePowerTick` samples total power on every hardware tick (same `LocalFeaturePolicy.SampleHardware` gate and cadence as the CPU chip: 1 s with Stats open, 2 s otherwise, at most once a second in games) into a 60-sample `PowerHistory`; the desktop Power chip (`ShowPowerChip`, `PowerChipText`, `PowerChipSparkPoints`, `MochiDock.Core.PowerChip`) and the Battery page (`PowerSampled`) read it, so neither resets on tab changes.
- **Power total:** `HardwareMonitorService.SamplePower` takes CPU package and memory power from the sensor reader (needs PawnIO) and, when that has none, from Windows' "Energy Meter" counters through `Services/EnergyMeterReader.cs` (PDH `\Energy Meter(RAPL_Package0_PKG|DRAM)\Power`, milliwatts, converted by `MochiDock.Core/PowerUsage.cs` `EnergyMeterPower`; returns null when the counters are missing, zero or implausible). GPU power comes from NVML or a sensor only. `PowerEstimator` still adds the fixed allowance and the result is always an estimate; it shows `-` only when no CPU and no GPU reading exists.
- **Update check:** `MochiDock.Core/ReleaseUpdate.cs` (`ReleaseVersion`, `UpdateFeed.Newest`: pure, picks the newest non-draft release of `sleepisfun17/MochiDock`, pre-releases only for a pre-release build, only `https://github.com/sleepisfun17/MochiDock/` pages) and `Services/UpdateCheckService.cs` (GET `/releases?per_page=10`, generic User-Agent, 10 s timeout; 404 while the repo is private is a quiet "could not check"). `ViewModels/MainViewModel.Updates.cs` runs it 30 s after start and every 12 hours when `AppSettings.CheckForUpdates` is on, shows the result in the quick settings header button (`SettingsCardView` `UpdateChip`/`UpdateChipAccent`, next to Reconnect; `UpdateChipPolicy` picks the state and text: the version (click checks), "Checking…", accent "Update to x" (click installs) or "x available" (click opens the release page), "Downloading N%" (click cancels), "Installing…"; `MainViewModel.UpdateChipClickAsync`), Settings > Data & diagnostics and the tray menu, and `OpenUpdatePage` opens the release page. An automatic check that finds a version not yet in `AppSettings.LastAnnouncedUpdate` (local-only, not exported) raises one capsule notice (`_noticeIsUpdate`, `UpdateAnnouncePolicy`, `TryShowUpdateNotice`; held back by gaming, lock, screen off, other notices, snooze and quiet hours and retried every 5 minutes); tapping it opens the quick settings. One-click update (`MainViewModel.InstallUpdateAsync`, after a confirmation, from Settings or the tray): only when the release has an asset named exactly `MochiDock-Setup-<version>.exe` under `https://github.com/sleepisfun17/MochiDock/releases/download/` with GitHub's `sha256:` digest and a plausible size (`UpdateFeed` sets `UpdateOffer.Installer`), and only for the installed copy (`UpdateInstaller.IsInstalledCopy`: the setup's uninstall `InstallLocation` equals the app folder). `Services/UpdateInstaller.cs` downloads to `%LocalAppData%\MochiDock\Updates`, hashing as it streams, deletes anything whose size or SHA-256 differs, starts the setup with `/VERYSILENT /SUPPRESSMSGBOXES /NORESTART /SP- /RELAUNCH` and the app shuts down; `installer/MochiDock.iss` restarts MochiDock on `/RELAUNCH` (`IsRelaunch`) and skips the PawnIO winget step then. The builds are unsigned, so the checksum and the fixed release URL are the trust anchor; never relax them. The app version comes from `<Version>` in `MochiDock.csproj`; `installer/MochiDock.iss` `MyAppVersion` must equal it (test `VersionSourceTests`).
- **WhatsApp is opt-in:** `AppSettings.EnableWhatsApp` defaults to off and `GowaService.Start()` is a no-op (no process, event listener or polling) while it is off; `CheckConnectionAsync` reports not connected and the tray status reads "WhatsApp: Off". `MigrateWhatsAppOptIn` (once, `WhatsAppOptInMigrated`) turns it on for old settings files that use a remote server or that have local session data under `%LocalAppData%\MochiDock\GOWA\storages`; fresh installs start off. The switch is the first row of the WhatsApp settings section. New installs also start with only Media, Stats, Weather and Prayer tabs on.
- **IMAP mail:** `Services/ImapMailService.cs` (an `IMailService` named `Webmail`) watches the INBOX of each `AppSettings.ImapAccounts` entry with MailKit (`Services/MailKitImapSession.cs`: TLS only, certificates validated, INBOX opened read-only unless the account's `MarkAsRead` is on, IDLE with a NOOP fallback). It remembers the newest UID at connect time and announces only later mail; a rejected login is not retried. App passwords live only in `Services/MailCredentialStore.cs` (DPAPI, `%LocalAppData%\MochiDock\mail-imap.dat`), never in settings, exports or logs. Removing an account deletes its password and shows a reminder in the Email section (`ImapAccountPolicy.RevokeUrl`/`RemovedNotice`: the preset's app-password page; no provider lets an app revoke its own app password). The uninstaller always deletes `mail-imap.dat`, `gowa-remote.dat` and `gcal.dat` before the keep-settings question (also when silent; an in-app update runs the setup, not the uninstaller, so it keeps them) and, when mail passwords existed, tells the user to revoke them at the provider (test `UninstallAlwaysDeletesSavedSecrets`). Provider presets, validation and the new-mail rule are pure code in `MochiDock.Core/ImapAccountPolicy.cs`; `MainViewModel.AddImapAccountAsync` tests the login before saving and `SettingsApply.MailAccounts` pushes the list to the service. Outlook.com personal accounts need OAuth and are not supported.
- Local GOWA defaults to `127.0.0.1:3099`, with webhook delivery to `http://127.0.0.1:47823/webhook`; settings can change both ports. Launch flags include `--webhook-events="message,message.ack" --auto-download-media=false`. API polling supplements webhook delivery. Quick reactions send emoji replies through `/send/message`, rather than native message reactions.
- **Email and Discord:** `CompositeMailService.cs` combines Mailspring's `%AppData%\Mailspring\edgehill.db` reader and Outlook Classic COM integration. Outlook runs through `MochiDock.Core/OutlookComReader.cs`. MochiDock is elevated but Outlook normally is not, and Windows blocks COM between them (`MK_E_UNAVAILABLE`), so when elevated the reader runs in `MochiDock.OutlookHelper` (`OutlookHelper/MochiDock.OutlookHelper.exe`, asInvoker, started with the shell's non-elevated token by `OutlookHelperHost.cs`) and relays mail over a user-only named pipe with a per-run secret; a non-elevated MochiDock runs the reader in-process. Never edit the helper to require elevation. Watched folders: every store's Inbox (its default inbox, or a folder named Inbox/受信トレイ) with all subfolders, plus any folder named in `AppSettings.OutlookTrackedFolders` (default 案件, Clients, Others; edited in settings.json) with all subfolders; Deleted/Junk/Sent/Drafts/Outbox and non-mail folders are skipped, and only unread mail received since monitoring began (minus 15 minutes) is considered, so old unread mail in large folders is never walked. The names reach the helper in a `config` pipe message. `AppSettings.OutlookOnlyListedFolders` (Email settings: "Only watch the folders listed below", default off) switches to the listed folders only: the Inbox and its other subfolders are then ignored (`OutlookFolderPolicy.IsWatched`), the helper receives the flag in the `config` pipe message (`only`), and the log line after each scan lists the watched folder paths. Mailspring's `MarkAsRead` does nothing (its database is opened read only); `IMailService.CanMarkAsRead` says whether a source really marks mail read (Outlook yes, Mailspring no, IMAP only with the account's "Mark as read on the server"), and the email card hides Mark Read through `MainViewModel.CanMarkCurrentEmailRead` when it would not. `DiscordNotificationService.cs` uses Windows `UserNotificationListener`; validate access in the deployed environment rather than assuming it succeeds. Verification codes for the Email card's Copy Code button come from `MochiDock.Core.VerificationCodeExtractor` (called through `Helpers/CodeDetectionHelper`): links, email addresses and domains are blanked first, then every candidate is scored (a token within three words after "code", "OTP", "kode" and similar wins, then uppercase or digit codes like `G-123456`, then 4-8 digits near a keyword; repeats and the subject add weight). Years, times, dates, money, phone groups and hyphenated lowercase words are never offered. Unit-tested in `VerificationCodeExtractorTests`.
- **Telemetry:** `FpsMonitorService.cs` consumes DXGI, D3D9 and DxgKrnl ETW events. `HardwareMonitorService.cs` uses NVIDIA NVML, Windows PDH/performance counters and `SensorService.cs` (LibreHardwareMonitorLib, lazy 2-second refresh, selection logic in `MochiDock.Core/SensorPicker.cs`) for real CPU/GPU temperature, GPU clock and GPU power. CPU temperature needs the PawnIO driver installed; without it the CPU temperature stays an estimate shown with `~` and is never used for alerts. GPU clock and power are never synthesized: they show `–` when no sensor provides them, with network adapter scoring and virtual-tunnel deprioritization (Tailscale, TAP, Hyper-V) from `NetworkPolicy.cs` and `NetworkService.cs`; no AMD ADL path is implemented. Weather parsing and display enforce invariant culture formatting. CPU System/User/Idle use Windows CPU-time deltas; effective GHz uses the Windows processor-performance counter and reported base clock. Missing samples show —; the CPU-time breakdown is unavailable above 64 logical processors. CPU temperature is estimated, and other readings include estimated or fixed fallbacks. Distinguish measured, estimated and unavailable data; do not promise universal hardware support or zero overhead.
- **Gaming:** detection includes `SHQueryUserNotificationState` and foreground-window/process checks. The window applies a `GamingTopOffset` in floating mode (zero offset in notch mode), `WS_EX_TRANSPARENT | WS_EX_NOACTIVATE` for click-through without focus stealing, and 500-ms `PolicyTick` `HWND_TOPMOST` re-assertion; it does not currently position itself using `GamingBottomMargin`. `LocalFeaturePolicy.Hide` exempts active games and pinned readouts from `HideInFullscreen`. Legacy exclusive fullscreen games bypass DWM scanout entirely; borderless windowed or Windows Fullscreen Optimizations (FSO) are required for non-injected desktop overlays.
- **Window-size shortcuts:** global hotkeys that resize the foreground window to a preset outer size in physical pixels and centre it on its monitor's work area (replacing the user's AutoHotkey WindowResizer script, which some anti-cheats block). `AppSettings.EnableWindowSizeShortcuts` (false for new installs), `WindowSizePresets` (defaults 1920x1080, 2560x1440, 1080x1920, 720x1280 on Ctrl+Alt+1-4) and `EnableWindowFlip` / `WindowFlipHotkey` (Ctrl+Alt+F; Ctrl+Alt+R stays the resolution toggle). Pure rules in `MochiDock.Core/WindowSizing.cs` (placement: centred, top/left-aligned when larger than the work area; shortcut conflicts with each other, the resolution toggle and Alt+Shift+S); Win32 in `Services/WindowResizerService.cs` (restore, `SetWindowPos`, reports the size the window actually took; never MochiDock, the desktop or the taskbar); registration in `MainWindow.WindowSizes.cs` (hotkey ids 9100-9108 and 9199, re-applied on `SettingsApply.Hotkey`); UI in `GamingSectionView.WindowSizes.cs`. Feedback is the capsule resolution notice. No keyboard hook or injection.
- **UI sounds and public defaults:** the notification pop (also the prayer Tone chime) and the petting chime are synthesised by `MochiDock.Core.UiSounds` (16-bit mono WAV in memory, about -6 dBFS, no click at either end); no audio file ships. New installs start with prayer times, the Japan and Indonesia holiday calendars and the window-size shortcuts off and an empty remote GOWA URL (empty falls back to the local engine); saved settings files keep their values.
- **Media and lyrics:** GSMTC supplies media state and controls. LRCLIB parsing supports multiple timestamps; synchronized display uses a timestamp-aware monotonic clock with zero Spotify offset and background STA pronunciation enrichment. `LyricRomanizerService.cs` handles Japanese, Korean and Chinese readings (see Lyrics rewrite below). Keep stale asynchronous results from replacing newer track state when changing this flow. A capsule lyric line wider than the capsule scrolls once, paced to its time on screen (`MainViewModel.CompactLineSeconds` -> `MarqueeTextBlock.PaceSeconds`, `MochiDock.Core.LyricScrollPace`: short start pause, user speed as the minimum, 240 DIP/s cap, 0.6 s end hold) instead of looping; titles and notices keep the looping marquee. `LrclibService` keeps a romaji transliteration (`MochiDock.Core.LyricScript.LooksLikeRomaji`) only as a last resort and keeps searching for a native-script record (cache format 4 refetches older picks).
- **Prayer:** `PrayerScheduleProvider.cs` supplies Aladhan schedules keyed by coordinates, method, location-local date and named time zone; `PrayerTimesService.cs` contains the approximate offline calculator. A 32-entry atomic cache persists under `%LocalAppData%\MochiDock\prayer-cache.json`. Today and tomorrow are loaded together; countdown ticks preserve API times and use absolute instants. The card plots a schematic prayer timeline with its peak at Dhuhr, shows dynamic qibla and labels offline calculations. Tone/Silent are authoritative; custom Adzan recording controls have been removed. Legacy recording settings are retained but ignored. Reminders are deduplicated; lock/resume does not replay missed sounds. Real audio/UI checks remain human-operated.
- **File drop:** `PhoneDropServer.cs` serves LAN-only HTTP on port `47824`, bound to the selected IPv4 address. A fresh secret link authenticates proposals and uploads; PC approval is required before file bodies are accepted. Limits: 10 files, 512 MiB/file, 1 GiB/request, two active uploads, 60-second approval and upload-idle timeouts, 15-minute session inactivity expiry. Staged writes never overwrite existing files. Explicit Stop, workstation lock and application exit cancel transfers and invalidate the session. HTTP provides no transport encryption; no firewall rules are changed.
- **Settings wiring:** `EnableGowa`, `EnableMascot`, `AutoNotchInGaming`, `GamingBottomMargin` and `GroupNotifications` were removed (no runtime consumer); old settings files that still contain them load normally because unknown JSON properties are ignored. `EnableAiUsageAlerts` now drives low-usage alerts (see the AI usage notes in docs/README.md). Verify consumers before documenting a setting as functional.

## 7. Contribution Conventions

These requirements guide new changes; they do not imply every existing service already follows them.

- Keep code comments and documentation in English.
- Update UI properties and bound collections on their owning WPF dispatcher. Prefer asynchronous file/network I/O and move blocking work off the UI thread while respecting COM and WinRT apartment requirements; use STA where required rather than blindly wrapping interop in `Task.Run`.
- Give new asynchronous work explicit ownership, cancellation and stale-result handling. Stop owned timers, listeners and processes and unsubscribe events when the feature or application shuts down.
- Preserve existing persistence compatibility. For persistence changes, prefer atomic writes and recovery that preserves unreadable user data; settings and tasks now queue atomic JSON saves; synchronous loading and fuller validation remain pending.
- Data paths go through `Services/AppDataPaths` (`Roaming` for settings, `Local` for caches, logs, sessions and sealed secrets). `MochiDock.Tests/TestDataIsolation.cs` redirects them to a temp folder in a module initializer, so tests never touch the real `%AppData%`/`%LocalAppData%`; new services compiled into the tests must use `AppDataPaths` for their default paths, and services must not save settings themselves (the settings owner does). Before this, `GowaService.ConfigureFromSettings` saved a blank test `AppSettings` over the real settings file on every test run.

Lyrics rewrite (2026-11-19, unit-tested and checked against the real Windows analyzer from a console harness; not seen in the running app): `LrclibService` and `LyricRomanizerService` were rewritten clean-room from public sources so the Oyenza Studio credit for them could be dropped; the public API and every caller are unchanged. Lookup ladder (`LrclibService.RunLookupAsync`): `/api/get` with album, then without album (both only when the duration is known), then `/api/search` by `track_name`/`artist_name`, then `/api/search?q=`; the first synced record that has at least `MinLines` timed lines and is within `MaxSyncDriftSeconds` of the track wins, while plain text (preferred) or an instrumental record is kept as the fallback; search results must reach `MatchScore` >= `MinScore`. 404 moves on; any other HTTP error, timeout or network error stops the lookup, sets `LastLookupFailed` and is not cached. Concurrent lookups of the same track share one request. Cache: memory (48 entries) plus one JSON file per track (`Format` 3, `Saved`, `Key`, `Lyrics`; at most 600 files) under `%LocalAppData%\MochiDock\Lyrics`; synced results live 30 days, plain/instrumental 7 days, misses 1 day; files from the old format are ignored and refetched. `ParseLrc` handles several time tags per line, `[mm:ss]`, `.xx`, `.xxx` and `:xx` fractions, `[offset:±ms]` (positive = earlier) and strips enhanced-LRC word tags. The pure romanization lives in Core and is unit-tested (`RomanizationTests`): `KanaRomanizer` (modified Hepburn: long vowels as written, ー repeats the vowel, っ doubles the consonant and is `t` before `ch`, ん is `n'` before a vowel or y, を is `o`), `HangulRomanizer` (Revised Romanization with linking, palatalisation, ㅎ aspiration, nasalisation and ㄹ/ㄴ assimilation; tensing is not written) and `LyricReading` (one segment per Japanese phrase from the analyzer's phrase starts with particles spaced and は/へ read wa/e; one per Chinese character; one per Korean word). Japanese readings come from Windows `JapanesePhoneticAnalyzer`, which fails with a COM error on MTA threads, so pronunciation always runs on an STA thread (`PronounceLine` hops to one); the analyzer's full-width ASCII is mapped back to the line's own text; a word it cannot read, or the whole line if it is unavailable, falls back to longest-match over `Assets/ja_readings.tsv.gz` (mecab-ipadic, NAIST notice). Chinese pinyin comes from `Assets/zh_pinyin.tsv.gz`: the first Unihan kMandarin reading per BMP character (Unicode 16.0.0, Unicode License v3 in `THIRD-PARTY-NOTICES.txt`), rebuilt with `tools/data/build-pinyin-table.ps1`; characters with several readings always get the most customary one (no word-level disambiguation). `LyricPronunciationPolicy.IsKana/IsHan/IsHangul` are now public and are the one definition of those ranges. The unreachable pause-line gap branch in `MainViewModel.OnTimelineUpdated` was removed (an empty line already clears the display).

WhatsApp read sync and the webhook relay: in Remote mode "read elsewhere" is detected only by GOWA's `message.ack` webhook (new messages come from REST polling). Receipts clear notifications through `AckReceiptPolicy.Decide`: `read-self` (read on another device) clears by message ids, or the whole chat when it has none; a plain `read` (what GOWA sends when you read an incoming message, and also when a contact reads one of yours, with no `is_from_me` in the payload) clears ONLY by ids and never a whole chat, which is safe because a contact reading your message names ids that match no incoming notification; an explicit `is_from_me == true` never clears. (A stricter rule that ignored plain `read` receipts broke read sync in practice.) GOWA delivers a webhook to several addresses one after another with long retries, so listing every dock in `--webhook` let an offline dock delay or lose the receipt for the others (the office dock stopped clearing when the main PC's dock was off). The shared-server installer therefore gives GOWA ONE loopback address, the relay `tools/gowa-relay` (`MochiDock.GowaRelay.exe`, task `MochiDock-GOWA-Relay`, 127.0.0.1:47830, listens on loopback only): it answers 200 at once and forwards the same body and headers to every address in `C:\ProgramData\MochiDockGowaServer
elay-targets.txt` in parallel (3 s timeout, one retry after 2 s, then dropped; the file is re-read when it changes; `relay.log` is size-capped and never contains a token). `install-gowa-server.ps1` installs both tasks and offers `-AddWebhookUrl` / `-RemoveWebhookUrl` to edit the list without a reinstall; `publish.ps1` and `tools/gowa-relay/publish.ps1` publish the relay, `tools/test-gowa-relay.ps1` is a loopback fan-out test (one live and one dead target). The pure rules (`WebhookRelayRules`, `AckReceiptPolicy`, `ReadSyncStatusText` in `MochiDock.Core/GowaWebhookRules.cs`) are tested and the relay compiles the same file. Diagnostics: `GowaService.LastReadReceiptAtUtc` / `RejectedWebhookCount` feed the "Last read receipt" line in Settings > WhatsApp. No catch-up clearing exists: the REST chat list is only known to carry `jid`, `name`, `last_message_time` and `archived` (the first poll logs the real field names as "[Chats] fields for account"), and no read or unread field was verified, so nothing is guessed; if a future server shows one (for example `unread_count`), poll it for chats with a visible notification.
